C unions — precise mechanics

The byte-level story of how unions work, how they sit in memory, and why DiplomatResult<T, E> is a tagged union under the hood. With actual hex dumps you could verify with printf("%02X").

The one-line definition

A union is one piece of memory you can read as any one of several types. All members start at the same address and share the same storage. Writing one member overwrites whatever bytes overlap with it.

Compare to a struct:

  • struct: members are side by side — total size is sum of members
  • union: members are on top of each other — total size is max of members

The sizing rules

For union U { T1 a; T2 b; ... Tn z; };:

sizing formulamemory
sizeof(U)  = max(sizeof(T1), sizeof(T2), ..., sizeof(Tn))
             rounded up to alignof(U)

alignof(U) = max(alignof(T1), alignof(T2), ..., alignof(Tn))

Union is as big as its largest member, aligned for its strictest member. That's it — three rules.

Example 1 — same-size members

same-size unionC
#include <stdio.h>

union Same4 {
    int    as_int;        // 4 bytes
    float  as_float;      // 4 bytes
    char   as_chars[4];   // 4 bytes
};

int main() {
    union Same4 u;
    u.as_int = 0x41424344;
    // size = 4
    // bytes (little-endian): 44 43 42 41

All three views are valid simultaneously. They're literally reading the same 4 bytes through different lenses. Writing through as_int changed what as_float and as_chars "see" — not because the union tracked the change, but because they all alias the same memory. This is called type punning.

This is the "union slack" problem. When the active member is smaller than the union, the unused bytes hold whatever was in that memory before — stack noise, leftover from a previous union value, a zero from calloc, anything. Reading the larger member is undefined behavior. The compiler will not warn you; the runtime won't catch it.

This is why Result<T, E> needs an external tag. Just looking at the 8 bytes can't tell you which member is "live" — both readings would produce some value, but only one is real. You need a separate bit somewhere that says "I last wrote to err" or "I last wrote to ok." The C language won't track this for you.

The tagged-union pattern (this is what DiplomatResult is)

tagged union — DiplomatResult shapeC
typedef struct {
    union {
        Color*     ok;     // valid when is_ok == true
        ColorError err;    // valid when is_ok == false
    } payload;             // 8 bytes
    bool is_ok;            // 1 byte tag
    // -- compiler inserts padding to align to 8 --
} DiplomatResult_Color_ColorError;

// sizeof = 16 (8 + 1 padded to 8-byte alignment)

Same struct, same size, different bytes. The byte at offset 8 (is_ok) is the only thing telling the caller which interpretation of bytes 0-7 is valid. Padding bytes 9-15 are inserted by the compiler to keep the struct aligned for arrays of these structs — they hold nothing useful.

How C# models this — [StructLayout(Explicit)]

C# can't say "union" directly. The managed type system doesn't allow arbitrary aliasing. But there's an escape hatch: [StructLayout(LayoutKind.Explicit)] + [FieldOffset(N)] lets you manually place fields at specific byte offsets, including overlapping ones.

C — the union we're modelingC
struct DiplomatResult {
    union {
        Color*     ok;
        ColorError err;
    } payload;
    bool is_ok;
};
C# — explicit-layout structC#
[StructLayout(LayoutKind.Explicit)]
internal unsafe struct DiplomatResult_Color_ColorError
{
    [FieldOffset(0)] public Raw.Color* Ok;
    [FieldOffset(0)] public ColorError Err;
    [FieldOffset(8)] public byte       IsOk;
}

The two [FieldOffset(0)] declarations tell the CLR: these two fields live at the same byte offset. Reading Ok and reading Err reads the same 8 bytes, interpreted differently. That's exactly the C union semantic.

Two C# gotchas:
  1. Use byte IsOk, not bool IsOk. Rust's bool is 1 byte; C#'s default marshaling treats bool as 4-byte BOOL. byte avoids the mismatch. Read it as IsOk != 0.
  2. Padding is inserted automatically. You don't declare the 7 bytes of trailing pad — the runtime adds them to round to 16-byte alignment. The struct is still 16 bytes even though you only declared fields at offsets 0 and 8.

"What if I read the wrong arm?" — the danger zone

dangerUB
var result = Raw.Color.Parse(...);

// Result came back as Err — IsOk == 0
// But we forgot to check the tag:
Color* ptr = result.Ok;
// ptr now points at: lower 4 bytes are 0x00000000 (the err value)
//                    upper 4 bytes are STACK GARBAGE (slack)
//                    full pointer: 0x????????00000000

// Dereferencing:
ptr->something;
// → AccessViolation, or worse: reads from some unrelated memory
//   that happens to look readable. Bug is non-deterministic and
//   may not surface in tests.
The check is non-negotiable. if (result.IsOk == 0) throw ... isn't a stylistic choice — it's the difference between a working binding and a security hole. The codegen always emits this check; the user can never bypass it by accident because the raw struct is internal and the idiomatic wrapper is the only way to call the FFI.

A complete worked program you can run

union_demo.c — self-contained, ~30 linesC
#include <stdio.h>
#include <stdint.h>
#include <stdbool.h>

typedef enum { Unknown = 0, BadFormat = 1 } ColorError;
typedef struct Color Color;  // opaque

typedef struct {
    union {
        Color*     ok;
        ColorError err;
    } payload;
    bool is_ok;
} DiplomatResult_Color_ColorError;

void print_bytes(const char* label, const void* p, size_t n) {
    printf("%s (%zu bytes): ", label, n);
    const uint8_t* b = p;
    for (size_t i = 0; i < n; i++) printf("%02X ", b[i]);
    printf("\n");
}

int main() {
    DiplomatResult_Color_ColorError ok_result;
    ok_result.payload.ok = (Color*)0x000001B45F2C8010ULL;
    ok_result.is_ok = true;

    // Zero-init err struct to make slack bytes deterministic
    // (in real Rust returns, slack is whatever the stack had).
    DiplomatResult_Color_ColorError err_result = {0};
    err_result.payload.err = Unknown;
    err_result.is_ok = false;

    printf("sizeof = %zu\n", sizeof(DiplomatResult_Color_ColorError));
    print_bytes("Ok ",  &ok_result,  sizeof(ok_result));
    print_bytes("Err",  &err_result, sizeof(err_result));
}
expected output (x64 little-endian)memory

Ok  (16 bytes): 10 80 2C 5F B4 01 00 00 01 00 00 00 00 00 00 00
Err (16 bytes): 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00

Verify this for yourself. Compile with gcc union_demo.c -o demo && ./demo (or cl union_demo.c on MSVC). The byte patterns will match exactly. This is the exact same byte stream that crosses our FFI boundary — Rust writes it, the OS pushes it onto the native return stack, C# reads it as DiplomatResult_Color_ColorError.

The endianness footnote

Notice the pointer 0x000001B45F2C8010 shows up as 10 80 2C 5F B4 01 00 00 in memory — byte order reversed. That's little-endian: the least significant byte comes first. x86 / x64 / ARM (in standard config) / RISC-V are all little-endian. PowerPC and SPARC are big-endian (the pointer would be 00 00 01 B4 5F 2C 80 10).

Doesn't matter for us in practice — Diplomat is built for x64 / ARM64, both little-endian. But if a tagged union ever crossed between machines of different endianness, the bytes would need swapping. (They don't, because FFI is in-process.)

TL;DR

  1. Union = shared storage. Members overlap at offset 0; size = max of members; alignment = max of members.
  2. Inactive members are uninitialized garbage. Reading them is undefined behavior. The compiler will not stop you.
  3. Tagged union = struct { union { ... } payload; tag; }. The tag tells the reader which arm is live.
  4. DiplomatResult<T, E> is a tagged union: 8-byte payload (Color* or 4-byte enum + slack) + 1-byte is_ok + 7 bytes padding = 16 bytes total.
  5. C# models unions with [StructLayout(Explicit)] + overlapping [FieldOffset] declarations. Same memory, two views.
  6. Always check the tag first. Always. No exceptions.
