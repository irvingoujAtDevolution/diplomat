Callbacks — every layer, every flavor

Three flavors exist in current Diplomat: impl Fn, impl FnMut, and impl Trait (where Trait is declared as a pub trait inside the bridge). The first two share one wire shape (DiplomatCallback<R>); the third has its own (a vtable struct). The diplomat macro and diplomat-runtime already generate the Rust and C-ABI sides — the .NET backend has to learn to consume them and advertise support. No core or macro changes should be needed for these shapes.
Correction from the previous draft. I previously claimed a third flavor "#[diplomat::callback]" trait attribute. That attribute does not exist. The actual trait flavor uses bare pub trait X { … } declarations inside the bridge — Diplomat picks them up automatically. I also claimed &dyn Fn was a possible flavor; it isn't — the AST lowering only matches syn::Type::ImplTrait, so callable parameters must be written as impl Fn / impl FnMut / impl SomeTrait. Sources verified: core/src/ast/types.rs:1040-1110, macro/src/snapshots/*.snap, runtime/src/callback.rs.

The six layers

A · user Rust B · Rust shim (macro-generated) C · C ABI wire form D · C# raw P/Invoke E · C# idiomatic wrapper F · user C#

Every flavor below is presented in those six layers. A & F are what humans write. B & C are what the diplomat macro and diplomat-runtime produce (already exist upstream). D & E are what we have to generate from the .NET backend.

The shared wire concept (read once)

C never had closures. Rust faked them across FFI by saying "here's the function pointer, here's a context pointer it should treat as its captured environment". Diplomat formalizes this as a 3-field struct:

runtime/src/callback.rs (existing, upstream)C ABI
#[repr(C)]
pub struct DiplomatCallback<ReturnType> {
    /// Context pointer — usually identifies a foreign-side object that
    /// owns the captured environment (in C#: a GCHandle to the delegate).
    pub data: *mut c_void,

    /// The trampoline. Variadic in the type signature so it can hold any
    /// concrete callback shape; the macro emits `mem::transmute` calls to
    /// cast it to the actual signature at call sites.
    pub run_callback: unsafe extern "C" fn(*mut c_void, ...) -> ReturnType,

    /// Optional cleanup — Rust calls this when it drops the callback.
    /// This is what makes ESCAPING callbacks work (callback stored on the
    /// Rust side, fired later, eventually destroyed).
    pub destructor: Option<unsafe extern "C" fn(*mut c_void)>,
}
Major insight, not in the previous draft: the destructor field already exists. That means escaping callbacks are represented by the ABI, but they are not automatic on the C# side. The backend must keep both the user target and the generated trampoline delegates rooted until Rust calls the destructor. The wire is not the bottleneck; the C# root/release dance is.

Flavor 1 — impl Fn(args) -> Ret

The bread-and-butter case.
Single anonymous function, no captured mutable state. C# users pass a Func<…> / Action<…> / lambda. Covers 80% of real-world use.

Layer A — user Rust

what users writeA · user-Rust
#[diplomat::bridge]
pub mod ffi {
    #[diplomat::opaque]
    pub struct Pixels(Vec<u8>);

    impl Pixels {
        pub fn visit(&self, on_pixel: impl Fn(u8)) {
            for &p in &self.0 { on_pixel(p); }
        }

        pub fn fold_sum(&self, seed: u32, step: impl Fn(u32, u8) -> u32) -> u32 {
            self.0.iter().fold(seed, |acc, &b| step(acc, b))
        }
    }
}

Layer B — Rust shim (what the macro emits)

macro output, abridged from callback_arguments.snapB · shim
use diplomat_runtime::*;
use core::ffi::c_void;

#[no_mangle]
extern "C" fn Pixels_visit(self_: &Pixels, on_pixel: DiplomatCallback<()>) {
    // Re-pack DiplomatCallback into something that satisfies `impl Fn(u8)`:
    let on_pixel = move |arg0: u8| unsafe {
        let _ = &on_pixel;  // keep `on_pixel` alive across the call
        std::mem::transmute::<
            unsafe extern "C" fn(*mut c_void, ...) -> (),
            unsafe extern "C" fn(*const c_void, u8) -> (),  // ← concrete sig
        >(on_pixel.run_callback)(on_pixel.data, arg0)
    };
    Pixels::visit(self_, on_pixel);   // the user's original method
    // on_pixel drops here → its `destructor` field is called if Some
}

#[no_mangle]
extern "C" fn Pixels_fold_sum(
    self_: &Pixels, seed: u32, step: DiplomatCallback<u32>,
) -> u32 {
    let step = move |a: u32, b: u8| unsafe {
        let _ = &step;
        std::mem::transmute::<
            unsafe extern "C" fn(*mut c_void, ...) -> u32,
            unsafe extern "C" fn(*const c_void, u32, u8) -> u32,
        >(step.run_callback)(step.data, a, b)
    };
    Pixels::fold_sum(self_, seed, step)
}

Why the transmute? The wire field run_callback is typed as variadic (extern "C" fn(*mut c_void, ...)) so one struct layout can hold any callback. At each call site, the macro knows the actual signature, casts the pointer to that signature, then invokes it. C ABI doesn't care — at the binary level it's just a jump to an address with registers loaded.

Layer C — C ABI / extern signature

what crosses the FFI boundaryC · wire
// As the C compiler sees it (or as P/Invoke sees it):
extern "C" {
    void Pixels_visit(
        const Pixels* self_,
        DiplomatCallback_void on_pixel,    // 3 × pointer-sized fields by value
    );
    uint32_t Pixels_fold_sum(
        const Pixels* self_,
        uint32_t seed,
        DiplomatCallback_u32 step,
    );
}

// Struct layout (same shape for any ReturnType — the type param only
// affects how Rust uses it, not the layout):
struct DiplomatCallback_void {
    void*  data;          // offset 0,  8 bytes on x64
    void*  run_callback;  // offset 8,  8 bytes
    void*  destructor;    // offset 16, 8 bytes (null = no destructor)
};
// Total: 24 bytes, passed BY VALUE.
By-value, 24 bytes. Important for the C# side: this struct is declared by value in the exported C ABI and in the C# P/Invoke signature. Do not hand-code it as a pointer parameter. ABI details are platform-specific: on Windows x64, non-1/2/4/8-byte aggregate arguments are generally passed indirectly by the ABI even though the source-level signature is by value.

Layer E — C# idiomatic wrapper (we generate this)

Pixels.cs (auto-generated)E · idiomatic
public unsafe partial class Pixels : IDisposable
{
    private sealed class CallbackState
        where TDelegate : Delegate
    {
        public required TDelegate UserDelegate;
        public Delegate Trampoline = null!;
        public Exception? Caught;
    }

    public void Visit(Action<byte> onPixel)
    {
        if (onPixel is null) throw new ArgumentNullException(nameof(onPixel));
        if (_inner is null) throw new ObjectDisposedException(nameof(Pixels));

        // 1. Build one rooted adapter object containing both the user delegate
        //    and the trampoline delegate. The GCHandle roots this adapter.
        var state = new CallbackState<Action<byte>> { UserDelegate = onPixel };
        DiplomatCallback_void_u8_Run trampoline = (IntPtr ctx, byte b) => {
            var s = (CallbackState<Action<byte>>)GCHandle.FromIntPtr(ctx).Target!;
            if (s.Caught is not null) return;
            try { s.UserDelegate(b); }
            catch (Exception e) { s.Caught = e; }
        };
        state.Trampoline = trampoline;

        // 2. Root the adapter. This is not a pinned handle; we need lifetime,
        //    not a stable managed-object address.
        GCHandle ctxHandle = GCHandle.Alloc(state);
        try
        {
            var wire = new DiplomatCallback_void_u8 {
                Data        = GCHandle.ToIntPtr(ctxHandle),
                RunCallback = Marshal.GetFunctionPointerForDelegate(trampoline),
                Destructor  = IntPtr.Zero,   // sync callback: C# owns Free()
            };

            Raw.Pixels.Visit(_inner, wire);
        }
        finally
        {
            ctxHandle.Free();
            GC.KeepAlive(state);
        }

        if (state.Caught is not null)
            throw new TargetInvocationException(state.Caught);
    }

    public uint FoldSum(uint seed, Func<uint, byte, uint> step)
    {
        // Same shape, but the trampoline must return a default value after
        // capturing an exception because exceptions must not cross the native
        // callback boundary.
        // Example policy: after the first exception, store it and return 0 for
        // every remaining callback invocation, then rethrow after Raw returns.
    }
}

Flavor 2 — impl FnMut(args) -> Ret

When the callback needs to mutate state.
Same wire as impl Fn. The only difference is Rust's borrow checker accepting &mut on the closure. From the C# user's perspective, identical — capturing mutable state works for Fn too in C# (no move distinction). The flavor only matters to the Rust author.

Layer A — user Rust

what users writeA · user-Rust
impl Pixels {
    pub fn count_above(&self, threshold: u8, mut tally: impl FnMut(u8)) -> u32 {
        let mut count = 0;
        for &p in &self.0 {
            if p > threshold {
                tally(p);     // ← needs &mut access to the closure's env
                count += 1;
            }
        }
        count
    }
}

Layer B — Rust shim

macro output (mutability flips the context-pointer pun)B · shim
#[no_mangle]
extern "C" fn Pixels_count_above(
    self_: &Pixels, threshold: u8, mut tally: DiplomatCallback<()>,
) -> u32 {
    let tally = move |arg0: u8| unsafe {
        let _ = &tally;
        std::mem::transmute::<
            unsafe extern "C" fn(*mut c_void, ...) -> (),
            unsafe extern "C" fn(*MUT c_void, u8) -> (),  // ← *mut, not *const
        >(tally.run_callback)(tally.data, arg0)
    };
    Pixels::count_above(self_, threshold, tally)
}
The mutability is a documentation thing at the ABI level. The first param of run_callback becomes *mut c_void instead of *const c_void, but binary calling convention doesn't distinguish. It exists so Rust's type system holds together; the C# side doesn't see a difference.

Layers C–F

Layer C, D, E, F are byte-for-byte identical to Flavor 1. The wire struct is the same. C# delegates close over mutable state without syntactic ceremony.

user C# — looks just like Flavor 1F · user-C#
var hits = new List<byte>();
uint n = px.CountAbove(threshold: 200,
    tally: b => hits.Add(b));      // mutates `hits` — fine
Console.WriteLine($"{n} pixels > 200; sample: [{string.Join(',', hits.Take(5))}]");
Implication for our codegen: we can collapse Flavors 1 and 2 into the same C# code path. The .NET surface doesn't need to distinguish Action<byte> from "Action<byte> that mutates" — that's not a C# concept. One codegen path covers both Rust signatures.

Flavor 3 — impl SomeTrait (multi-method interface)

The "C# interface" experience.
When Rust needs multiple related operations from the caller — not one function, a coherent object. Rust declares pub trait X { fn a(&self, …); fn b(&self, …); } inside the bridge. C# users implement an interface.

Layer A — user Rust

what users writeA · user-Rust
#[diplomat::bridge]
pub mod ffi {
    #[diplomat::opaque]
    pub struct Pixels(Vec<u8>);

    // Declare a trait inside the bridge — Diplomat picks it up.
    pub trait PixelSink: std::marker::Send {
        fn on_start(&self);
        fn on_pixel(&self, p: u8);
        fn on_end(&self, total: u32);
    }

    impl Pixels {
        // Take any implementor.
        pub fn stream_to(&self, sink: impl PixelSink) {
            sink.on_start();
            for &p in &self.0 { sink.on_pixel(p); }
            sink.on_end(self.0.len() as u32);
        }
    }
}

Layer B — Rust shim (vtable, not DiplomatCallback)

macro output, abridged from traits.snapB · shim
// Diplomat generates a vtable struct (NOT a DiplomatCallback<_>):
#[repr(C)]
pub struct PixelSink_VTable {
    pub destructor: Option<unsafe extern "C" fn(*const c_void)>,
    pub size: usize,
    pub alignment: usize,
    pub run_on_start_callback: unsafe extern "C" fn(*const c_void),
    pub run_on_pixel_callback: unsafe extern "C" fn(*const c_void, u8),
    pub run_on_end_callback:   unsafe extern "C" fn(*const c_void, u32),
}

// And a struct pairing the foreign object pointer with its vtable:
#[repr(C)]
pub struct DiplomatTraitStruct_PixelSink {
    data: *const c_void,
    pub vtable: PixelSink_VTable,
}
unsafe impl std::marker::Send for DiplomatTraitStruct_PixelSink {}

// Rust gets a blanket impl that satisfies the user's `impl PixelSink` bound:
impl PixelSink for DiplomatTraitStruct_PixelSink {
    fn on_start(&self) {
        unsafe { ((self.vtable).run_on_start_callback)(self.data); }
    }
    fn on_pixel(&self, p: u8) {
        unsafe { ((self.vtable).run_on_pixel_callback)(self.data, p); }
    }
    fn on_end(&self, total: u32) {
        unsafe { ((self.vtable).run_on_end_callback)(self.data, total); }
    }
}

// Plus a Drop impl that fires the destructor when the trait struct drops:
impl Drop for DiplomatTraitStruct_PixelSink {
    fn drop(&mut self) {
        if let Some(destructor) = self.vtable.destructor {
            unsafe { (destructor)(self.data); }
        }
    }
}

#[no_mangle]
extern "C" fn Pixels_stream_to(
    self_: &Pixels, sink: DiplomatTraitStruct_PixelSink,
) {
    Pixels::stream_to(self_, sink)
}

Layer C — C ABI / wire form (bigger struct)

what crosses the boundaryC · wire
// Total size: 8 bytes (data) + sizeof(VTable):
//   destructor(8) + size(8) + alignment(8) + 3 × fn ptr (24) = 48
// → DiplomatTraitStruct_PixelSink is 56 bytes, passed BY VALUE.

struct PixelSink_VTable {
    void*  destructor;       // 0,  may be null
    size_t size;             // 8,  size of the foreign object (informational)
    size_t alignment;        // 16, alignment of the foreign object
    void*  run_on_start;     // 24
    void*  run_on_pixel;     // 32
    void*  run_on_end;       // 40
};

struct DiplomatTraitStruct_PixelSink {
    const void*       data;
    PixelSink_VTable  vtable;   // inlined, not pointer-to
};
Why inline the vtable instead of pointer-to-vtable (like C++)? Because the vtable comes from C# at call time — there's no static "class vtable" the way C++ has. Each instance of the trait object carries its own vtable inline, populated by C# when constructing the wire struct. Costs more bytes per call (56 vs ~16), saves a pointer chase.

Layer E — C# idiomatic surface (interface + adapter)

The interesting thing about Flavor 3: the idiomatic surface is a C# interface users implement, plus an internal adapter that wires it to the vtable. This is the most "object-oriented" of the three.

Pixels.cs + IPixelSink.cs (auto-generated)E · idiomatic
// Generated as the user-facing interface:
public interface IPixelSink
{
    void OnStart();
    void OnPixel(byte p);
    void OnEnd(uint total);
}

// Generated wrapper method on the consumer opaque:
public unsafe partial class Pixels
{
    private sealed class PixelSinkAdapter
    {
        public required IPixelSink Sink;
        public PixelSink_RunOnStart OnStart = null!;
        public PixelSink_RunOnPixel OnPixel = null!;
        public PixelSink_RunOnEnd OnEnd = null!;
        public PixelSink_Destructor Destructor = null!;
        public Exception? Caught;
    }

    public void StreamTo(IPixelSink sink)
    {
        if (sink is null) throw new ArgumentNullException(nameof(sink));
        if (_inner is null) throw new ObjectDisposedException(nameof(Pixels));

        // 1. Root one adapter object. It owns the user's sink and all
        //    trampoline delegates. This is lifetime rooting, not pinning.
        var adapter = new PixelSinkAdapter { Sink = sink };

        // 2. Build the trampolines — each one recovers `sink` from the
        //    adapter GCHandle and forwards to the interface method.
        adapter.OnStart = (IntPtr d) => {
            var a = (PixelSinkAdapter)GCHandle.FromIntPtr(d).Target!;
            if (a.Caught is not null) return;
            try { a.Sink.OnStart(); }
            catch (Exception e) { a.Caught = e; }
        };
        adapter.OnPixel = (IntPtr d, byte p) => {
            var a = (PixelSinkAdapter)GCHandle.FromIntPtr(d).Target!;
            if (a.Caught is not null) return;
            try { a.Sink.OnPixel(p); }
            catch (Exception e) { a.Caught = e; }
        };
        adapter.OnEnd = (IntPtr d, uint t) => {
            var a = (PixelSinkAdapter)GCHandle.FromIntPtr(d).Target!;
            if (a.Caught is not null) return;
            try { a.Sink.OnEnd(t); }
            catch (Exception e) { a.Caught = e; }
        };
        adapter.Destructor = (IntPtr d) => GCHandle.FromIntPtr(d).Free();

        GCHandle adapterHandle = GCHandle.Alloc(adapter);

        // 3. Fill the wire struct.
        var wire = new DiplomatTraitStruct_PixelSink {
            Data = GCHandle.ToIntPtr(adapterHandle),
            VTable = new PixelSink_VTable {
                Destructor  = Marshal.GetFunctionPointerForDelegate(adapter.Destructor),
                Size        = 0,     // informational; we don't expose Rust-side size
                Alignment   = 0,
                RunOnStart  = Marshal.GetFunctionPointerForDelegate(adapter.OnStart),
                RunOnPixel  = Marshal.GetFunctionPointerForDelegate(adapter.OnPixel),
                RunOnEnd    = Marshal.GetFunctionPointerForDelegate(adapter.OnEnd),
            }
        };

        // 4. NOTE: NO `adapterHandle.Free()` here — the Rust side will call our
        //    Destructor when the trait struct drops, which calls Free().
        //    Because the adapter owns every trampoline delegate, rooting the
        //    adapter roots every function pointer too.
        try
        {
            Raw.Pixels.StreamTo(_inner, wire);
        }
        finally
        {
            GC.KeepAlive(adapter);
        }

        if (adapter.Caught is not null) throw new TargetInvocationException(adapter.Caught);
    }
}
Subtle: who frees the adapter handle? Look carefully — there's no adapterHandle.Free() in finally. Instead, the Destructor trampoline calls GCHandle.FromIntPtr(d).Free(). The handle points to an adapter object that owns the user IPixelSink and every trampoline delegate. This is what makes escaping callbacks safe: Rust signals "done with this object" by calling the destructor, which releases the C# GCHandle, which then allows the adapter, sink, and delegates to be collected. For a synchronous StreamTo this fires immediately on return; for an opaque that stores the sink, it fires whenever Rust drops it. One bug here = a leak or a use-after-free.

Phasing

  1. Phase 1 (~1 week): impl Fn + impl FnMut (sync only — no escaping). Smoke crate gets Pixels::visit and Pixels::count_above; ~6 C# test cases.
  2. Phase 2 (~1 week): impl Trait with destructor-driven lifetime. Smoke crate gets pub trait PixelSink + Pixels::stream_to; C# interface generation.
  3. Phase 3 (required for IronRDP-style stored callbacks): Escaping callbacks via opaques that store a DiplomatCallback — the wire's already capable, but C# needs a rooted adapter object whose destructor releases both the user target and trampoline delegates. This is not just surface polish if a consumer stores callbacks and invokes them after the original P/Invoke call returns.
Bottom line. Phases 1+2 together are ~2 weeks for the full synchronous callback/interface story. No diplomat-core changes, no macro changes are expected for these shapes — the upstream sides are already done. IronRDP-style stored callbacks should be treated as Phase 3 work, not an optional nice-to-have.
