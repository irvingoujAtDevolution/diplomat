DiplomatWrite — a layered walkthrough

The writer pattern. Rust can't return a String across FFI directly — its heap allocator is its own. Instead, Rust functions take a caller-provided writer, append UTF-8 bytes into it, and if the buffer fills up, call back into the caller to grow it. From the user's perspective in C# this looks like return string; under the hood it's a bidirectional dance with function pointers crossing the FFI boundary. The #1 missing feature for binding real Rust libraries.
user code C# idiomatic (auto-gen) C# raw P/Invoke (auto-gen) C ABI contract (binary) Rust shim (macro-gen) callback into C# (grow buffer)

The problem: Rust can't return String

You'd expect Rust to write something like:

what we'd like to writeaspiration
// Doesn't work for FFI!
pub fn describe(&self) -> String {
    format!("Color(brightness={})", self.brightness)
}

But String is a Rust-specific type — it's a pointer + length + capacity that came from Rust's allocator. If you returned it across the FFI boundary, the C# side would see three numbers but couldn't free the pointer (C#'s allocator doesn't know Rust's heap). Even if you tried to copy the bytes, the lifetime is wrong — when does Rust free the original? Who owns what?

The fundamental issue. Cross-FFI ownership of heap-allocated growable buffers doesn't work. The allocator that malloc'd the bytes has to be the one that frees them. String's invariants live entirely on the Rust side; you can't smuggle them across.

The fix: caller-provided writer

Flip the ownership: the caller (C#) owns the buffer. Rust just writes into it.

what Rust actually writeshow it really works
use std::fmt::Write;

pub fn describe(&self, write: &mut DiplomatWrite) {
    let _ = write!(write, "Color(brightness={})", self.brightness);
    //         ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
    //         standard `write!` macro on the writer — same code Rust
    //         would write for any other Write-impl target
}

DiplomatWrite implements std::fmt::Write, so all the normal write! / writeln! / format_args! machinery just works. Rust feels like it's "returning a string"; it's actually appending bytes to a buffer the caller passed in.

What if the buffer isn't big enough?

Then Rust calls back into the caller to grow it. The writer struct carries a grow function pointer (registered by C# at the start of the call). Rust invokes it when it needs more bytes; C# reallocates the buffer and updates the pointer + capacity. Function pointer marshaling crosses the FFI boundary in the opposite direction — that's the load-bearing part of this design.

The example

One simple, end-to-end:

dotnet_smoke/src/lib.rsrust source
impl Color {
    /// Returns a human-readable description. From C# this looks like
    /// `string desc = color.Describe();`. Under the hood, C# allocates
    /// a writer, Rust appends UTF-8 bytes into it, C# extracts the
    /// string and frees the buffer.
    pub fn describe(&self, write: &mut DiplomatWrite) {
        use std::fmt::Write;
        let _ = write!(write, "Color(brightness={})", self.brightness);
    }
}

Goal: from C# the user writes string desc = color.Describe(); and gets "Color(brightness=128)" back. Every layer between is generated.

Layer 1 — The macro-expanded extern

generated by #[diplomat::bridge]rust shim
#[no_mangle]
pub unsafe extern "C" fn Color_describe(
    handle: *const Color,
    write: *mut diplomat_runtime::DiplomatWrite,   // ← writer comes IN as a param
) {                                                 // ← no return value (the write IS the return)
    let this: &Color = &*handle;
    let write: &mut DiplomatWrite = &mut *write;
    this.describe(write);
    write.flush();   // notify the caller "I'm done writing"
}

Key shape: the writer is a parameter, not a return value. At the C ABI level, this function returns void. The "return value" lives in the bytes that got appended to the writer's buffer.

Layer 2 — The DiplomatWrite struct (the contract)

This is the load-bearing struct. Rust defines it in diplomat_runtime; the C# binding mirrors its layout exactly.

diplomat_runtime/src/write.rs (sketch)runtime
#[repr(C)]
pub struct DiplomatWrite {
    pub context: *mut c_void,       // caller-specific handle (for callbacks)
    pub buf:     *mut u8,            // pointer to the byte buffer (caller-owned)
    pub len:     usize,              // bytes written so far
    pub cap:     usize,              // total capacity
    pub flush:   extern "C" fn(*mut c_void),                 // called when Rust is done
    pub grow:    extern "C" fn(*mut c_void, usize) -> bool,  // called when buffer is full
}

// Rust impls std::fmt::Write on it; write_str calls grow() if needed,
// then memcpys the bytes into buf, advances len.
FieldSize (x64)Purpose
context8 bytesOpaque handle. Caller stuffs whatever it needs in here (e.g., a GCHandle to the C# side). Rust passes it back when calling the callbacks.
buf8 bytesPointer to the caller-allocated byte buffer. Rust writes into this.
len8 bytesHow many bytes Rust has written so far. Starts at 0, grows.
cap8 bytesTotal bytes the buffer can hold. If len + new_bytes > cap, Rust calls grow.
flush8 bytesFunction pointer. Rust calls when done writing. Caller can use it to do final cleanup if needed.
grow8 bytesFunction pointer. Rust calls with a requested new capacity. Caller reallocates, updates buf and cap, returns true on success.

Total: 48 bytes. Six 8-byte fields, no padding.

The function pointers are the magic. They let Rust call back into C# at runtime. C# allocates the buffer; if Rust exceeds the capacity, C# gets a chance to grow it. This is the only way to handle "writes of arbitrary size" without precommitting to a fixed buffer size or doing N-pass writing.

Layer 3 — The C# raw struct

DiplomatWriteable.cs (runtime helper)C# raw
[UnmanagedFunctionPointer(CallingConvention.Cdecl)]
delegate void WriteFlush(IntPtr context);

[UnmanagedFunctionPointer(CallingConvention.Cdecl)]
[return: MarshalAs(UnmanagedType.U1)]
delegate bool WriteGrow(IntPtr context, nuint capacity);

[StructLayout(LayoutKind.Sequential)]
public struct DiplomatWriteable : IDisposable
{
    IntPtr context;
    IntPtr buf;
    nuint  len;
    nuint  cap;
    IntPtr flush;   // unmanaged function pointer (held as IntPtr)
    IntPtr grow;    // unmanaged function pointer

    public DiplomatWriteable()
    {
        // Allocate buffer with C# allocator (Marshal.AllocHGlobal — unmanaged).
        // We pin function pointers via Marshal.GetFunctionPointerForDelegate.
        WriteFlush flushDelegate = Flush;
        WriteGrow  growDelegate  = Grow;

        context = IntPtr.Zero;
        buf     = Marshal.AllocHGlobal(64);     // initial capacity
        len     = 0;
        cap     = 64;
        flush   = Marshal.GetFunctionPointerForDelegate(flushDelegate);
        grow   = Marshal.GetFunctionPointerForDelegate(growDelegate);
    }

    public string ToUnicode()
    {
        // After Rust has written, extract a managed string.
        return Marshal.PtrToStringUTF8(buf, (int)len);
    }

    public void Dispose()
    {
        if (buf != IntPtr.Zero) {
            Marshal.FreeHGlobal(buf);
            buf = IntPtr.Zero;
        }
    }

    private static void Flush(IntPtr context) { /* nothing to do */ }

    private unsafe static bool Grow(IntPtr context, nuint capacity)
    {
        // Rust asked for at least `capacity` bytes. Reallocate.
        // ... read DiplomatWriteable from context, double capacity, ReAllocHGlobal ...
        return true;
    }
}
The function pointer pinning matters. Marshal.GetFunctionPointerForDelegate requires the delegate to stay alive (not be garbage-collected) for as long as the pointer is used. If we let the delegate go out of scope, the GC reclaims it, the function pointer points at freed memory, Rust calls it during grow → access violation. The DiplomatWriteable struct has to hold references to the delegates (typically as private fields) for its lifetime.

Layer 5 — C# idiomatic: two overloads, not one

This is the part I got wrong in the first draft. Checking the actual picky-rs generated bindings: the codegen emits two methods per write-using Rust function. One mirrors the Rust signature directly; the other is a convenience overload that hides the writer machinery. The Rust signature itself stays as &mut DiplomatWrite at every layer — the "returns string" form is C# binding sugar, not a transformation of the underlying contract.

Form 1 — explicit, mirrors the Rust signature

Color.cs (codegen) — caller manages the writerC# idiomatic
public void Describe(DiplomatWriteable writer)
{
    unsafe
    {
        if (_inner == null) throw new ObjectDisposedException(nameof(Color));
        Raw.Color.Describe(_inner, &writer);
        // No string returned — the caller already has the writer; they
        // can read it themselves via writer.ToUnicode() when they're done.
    }
}

This form is useful when the caller wants to reuse a writer across multiple calls (one allocation, many appends) or has specific lifetime requirements. Power-user form.

Form 2 — convenience, auto-allocates and returns string

Color.cs (codegen) — convenience overloadC# idiomatic
public string Describe()
{
    unsafe
    {
        if (_inner == null) throw new ObjectDisposedException(nameof(Color));
        DiplomatWriteable writer = new DiplomatWriteable();   // 1. allocate buffer + register callbacks
        Raw.Color.Describe(_inner, &writer);                 // 2. Rust writes into writer.buf
        string retVal = writer.ToUnicode();                    // 3. extract UTF-8 bytes as managed string
        writer.Dispose();                                       // 4. free the buffer
        return retVal;
    }
}

This is what 99% of C# code will use: string desc = color.Describe();. The writer exists, but the binding hides it.

Both overloads exist on the same class with the same name. C# overload resolution picks based on whether the caller passes a writer. color.Describe(myWriter) → Form 1. color.Describe() → Form 2.

End-to-end data flow — the buffer dance

Step-by-step, including the case where the buffer has to grow:

1. C# allocates writer
new DiplomatWriteable() calls Marshal.AllocHGlobal(64) — unmanaged 64-byte buffer. Sets cap = 64, len = 0, registers flush and grow function pointers via GetFunctionPointerForDelegate.
↓
2. C# calls Rust
Raw.Color.Describe(_inner, &writer) — P/Invoke. Native stack carries opaque Color* + pointer to our 48-byte DiplomatWriteable struct.
↓
3. Rust enters describe()
write!(write, "Color(brightness={})", 128) — Rust's format machinery starts producing bytes.
↓
4. Rust writes "Color(brightness=128)" — 22 bytes
Fits in cap=64. len += 22, bytes memcpy'd into buf[0..22]. No grow needed.
↓
5. Rust returns, C# resumes
Native stack unwound. writer.len == 22, writer.buf[0..22] holds the UTF-8 bytes.
↓
6. C# extracts string
Marshal.PtrToStringUTF8(buf, 22) — reads UTF-8 bytes, converts to a managed UTF-16 string. Returns "Color(brightness=128)".
↓
7. using-scope exits, buffer freed
writer.Dispose() calls Marshal.FreeHGlobal(buf). Unmanaged buffer returned to the OS.

What happens if the buffer is too small?

Same flow, but step 4 splits in two — first attempt overflows cap, triggers the grow callback.

4a. Rust tries to write 100 bytes, cap is only 64
Rust's std::fmt::Write impl checks len + needed > cap. Calls (writer.grow)(writer.context, 128) — function pointer call back into C#.
↓
4b. C# Grow() runs (callback)
Delegate registered at step 1 is now invoked. Reallocates buffer to at least 128 bytes via Marshal.ReAllocHGlobal(buf, 128). Updates writer.buf + writer.cap. Returns true.
↓
4c. Rust resumes write
Re-reads writer.buf and writer.cap, copies bytes in. Loop until done.

The callback is the only direction C# ← Rust runtime can flow. Marshal.GetFunctionPointerForDelegate is how we set it up; the delegate object must outlive the call so its thunk stays valid.

The fallible variant

Some Rust APIs return Result<(), E> alongside the writer — formatting can fail (e.g., invalid input). picky-rs uses this pattern heavily:

    -> Result<(), Box<PickyError>>
{
    self.cert.to_pem()
        .map(|pem| { let _ = write!(write, "{pem}"); })
        .map_err(...)
}

C# binding combines DiplomatWrite + Result machinery:

        using var writer = new DiplomatWriteable();

Two crossings: the writer for the success-side bytes, the Result for the failure path. Composes naturally with the Result machinery we already shipped.

Pitfalls

1. Delegate lifetime. Marshal.GetFunctionPointerForDelegate returns a pointer that's only valid as long as the delegate is alive. If the binding constructs the delegates locally in the new DiplomatWriteable() ctor but doesn't hold references, the GC reclaims them and Rust's callback into a freed thunk crashes. Hold them as fields on the struct.
2. UTF-8 boundaries. Rust writes UTF-8 bytes; C#'s Marshal.PtrToStringUTF8 reads them. The bytes-to-chars conversion happens on C#'s side. If the byte stream is partially-written and Rust panics mid-write, len may point at a position inside a multi-byte sequence — extracting could yield a malformed string. Mitigated by Rust only calling flush when the write is complete.
3. Native heap, not managed. The buffer is allocated via Marshal.AllocHGlobal (unmanaged heap), not new byte[]. This matters for cross-FFI pointer stability (managed arrays can move; unmanaged can't) and for ownership (we explicitly free it; the GC never touches it). Forgetting the using leaks unmanaged memory.
4. Exception safety inside the callback. If Grow throws (e.g., OOM), the exception is in C# land. But Rust is between us and the throw — unwinding through native code is undefined behavior. The Grow callback must catch any exception and return false instead of unwinding.
5. Initial buffer size. 64 bytes is fine for short strings (most error messages, names); for large outputs (PEM certificates, hex dumps) the grow callback will be invoked multiple times. Could be tuned — start at 256 or 1024, exponential growth. Not blocking, but worth knowing.

TL;DR

  1. Rust can't return String across FFI — heap-owned-by-Rust crosses badly. Invert ownership: caller provides the buffer.
  2. DiplomatWrite is a 48-byte struct — pointer to caller-owned buffer + length + capacity + flush/grow function pointers.
  3. If the buffer is too small, Rust calls back into C# via the function pointer. Bidirectional FFI: data goes Rust→C# via the buffer, control goes C#→Rust via the call, callback goes Rust→C# via the function pointer.
  4. Rust signature stays &mut DiplomatWrite at every layer. The "return string" form is C# binding sugar — picky-rs generates two overloads per Rust function: void Foo(DiplomatWriteable w) (explicit) and string Foo() (convenience, auto-allocates). 99% of users call the convenience form.
  5. This is the #1 missing feature for binding real Rust libraries (16/22 picky-rs modules use it).
  6. The codegen work is moderate: one runtime helper file (DiplomatWriteable.cs, ~70 lines), one new arm in lower_return, and emitting two idiomatic methods per write-using Rust function. Less invasive than Result was, but a touch more than I initially estimated.
