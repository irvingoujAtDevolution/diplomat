Option<T> — a layered walkthrough

Rust's maybe a value, maybe nothing meets C#'s null story. Unlike Result<T, E> (errors-as-values), Option is not about failure — just absence. The C# binding maps it to nullable types, not exceptions. Two distinct paths under the hood depending on whether the inner type carries null natively (pointers) or needs a tag (value types).
user code C# idiomatic (auto-gen) C# raw P/Invoke (auto-gen) C ABI contract (binary) Rust shim (macro-gen) Path A — native-nullable (pointers) Path B — tagged Option (value types)

Option vs Result — what's different

Result<T, E> — "did this fail?" errors 
// Rust: returns Ok or Err with reason
fn parse(s: &str) -> Result<Color, ParseError>

// C#: throw on Err, success returns
try { var c = Color.Parse(s); }
catch (ColorErrorException ex) { ... }
Option<T> — "is this here?" absence 
// Rust: returns Some or None, no reason
fn find(&self, key: &str) -> Option<Color>

// C#: null = None, otherwise the value
var c = registry.Find(key);
if (c is null) { ... }
Semantic difference matters. Result encodes failure — something went wrong, here's why. Option encodes absence — the thing might just not exist, no error semantics. C# already has null for absence; throwing on null would be weird (you'd write try { ... } catch (NotFoundException) when the API said "this might not be there"). So Option maps to nullable returns, not exceptions.

The C# null story

C# has two flavors of null, and Option maps to whichever fits the inner type:

Inner type C# return type How null is represented Mechanism
Box<Color> (managed wrapper class) Color? The reference itself can be null Nullable reference types (C# 8+)
&Color (borrowed opaque) Color? Pointer can be null Same — reference nullability
u32 (primitive) uint? i.e. Nullable<uint> 16-byte struct with tag + value Nullable<T> generic
Point2D (struct) Point2D? i.e. Nullable<Point2D> struct holds value + flag Nullable<T> generic

Pointers can be null natively — no extra storage needed. Value types cannot — C# wraps them in Nullable<T> which carries an explicit HasValue flag alongside the value. The shape of the wire bytes mirrors this distinction.

The two examples

One method per path — the simplest cases that exercise the divide:

  • Path A — Color::find_by_name(name: &DiplomatStr) -> Option<Box<Color>> — known name returns a Color, unknown name returns None. Native-nullable pointer.
  • Path B — Color::default_brightness() -> Option<u8> — sometimes returns a default brightness, sometimes "no opinion." Tagged Option struct on the wire.
dotnet_smoke/src/lib.rs rust source 
impl Color {
    /// Path A — owned opaque option. Pointer is null when None.
    pub fn find_by_name(name: &DiplomatStr) -> Option<Box<Color>> {
        match name {
            b"red"   => Some(Box::new(Color { brightness: 255 })),
            b"black" => Some(Box::new(Color { brightness: 0 })),
            _        => None,
        }
    }

    /// Path B — primitive option. Needs a tagged struct on the wire.
    pub fn default_brightness() -> Option<u8> {
        Some(128)  // could be None depending on state
    }
}

HIR splits the cases

The same Rust Option<T> hits two different HIR shapes depending on T:

diplomat-core's hir::ReturnType for Option
// Rust source:                    HIR:
fn find_by_name(...)               ReturnType::Infallible(
    -> Option<Box<Color>>             SuccessType::OutType(Type::Opaque(opaque_path_with_optional))
                                   )

fn default_brightness()            ReturnType::Nullable(
    -> Option<u8>                     SuccessType::OutType(Type::Primitive(U8))
                                   )
Why the split. HIR collapses Option<Box<T>> into Infallible because the pointer carries the null natively — no extra tag needed on the wire. For any other T (primitive, struct, enum) the wire needs an explicit "is this Some?" tag, so it goes through Nullable which lowers to DiplomatOption<T> (= DiplomatResult<T, ()> in the runtime). Same machinery as Result, with unit error.

Path A — native-nullable pointer (Option<Box<T>>)

Layer 1 — Rust shim (macro-gen)

generated by #[diplomat::bridge] rust shim 
#[no_mangle]
pub unsafe extern "C" fn Color_find_by_name(
    name: DiplomatStrSlice,
) -> *mut Color {        // ← plain pointer, null = None
    let bytes: &[u8] = name.into();
    match Color::find_by_name(bytes) {
        Some(boxed) => Box::into_raw(boxed),   // valid pointer
        None        => core::ptr::null_mut(),  // null pointer
    }
}
No wrapper struct needed. The pointer IS the discriminant — null means None, anything else means Some. Zero extra bytes on the wire vs a non-Option opaque return.

Layer 2 — C ABI bytes

Some(...) on the wireC ABI
// 8 bytes total — just a pointer
Color* ret = 0x000001B45F2C8010;
// → not null, valid heap pointer
None on the wireC ABI
// 8 bytes total — null
Color* ret = 0x0000000000000000;
// → null, indicates None

Layer 3 — C# raw extern

RawColor.cs (codegen)C# raw
[DllImport(NativeLib, EntryPoint = "Color_find_by_name", CallingConvention = CallingConvention.Cdecl)]
public static extern Color* FindByName(DiplomatSliceU8 name);
// ↑ same as a non-optional opaque return — the pointer is just allowed to be null
The raw layer needs zero changes. Already-generated opaque returns already declare Color*, which is intrinsically nullable. The Option-ness is a property of how the idiomatic wrapper handles the result, not of the wire shape.

Layer 4 — C# idiomatic wrapper (the null check)

Color.cs (codegen)C# idiomatic
public static Color? FindByName(string name)
{
    unsafe
    {
        byte[] nameBytes = Encoding.UTF8.GetBytes(name);
        fixed (byte* namePtr = nameBytes)
        {
            Raw.Color* result = Raw.Color.FindByName(new DiplomatSliceU8 {
                Ptr = namePtr,
                Len = (nuint)nameBytes.Length,
            });
            return result == null ? null : new Color(result);
            //     ^^^^^^^^^^^^^^^^^^^^^^^^   The whole Option story.
        }
    }
}

Two new things vs a non-optional opaque return:

  • Return type is Color? (nullable reference type) instead of Color — signals to C# 8+ that null is a possible value.
  • Body conditionally wraps: result == null ? null : new Color(result). The non-option path was return new Color(result) unconditionally.

Layer 5 — User call site

idiomatic useuser code

Path B — tagged Option for value types (Option<primitive | struct>)

Layer 1 — Rust shim (macro-gen)

generated by #[diplomat::bridge] rust shim 
#[no_mangle]
pub unsafe extern "C" fn Color_default_brightness()
    -> diplomat_runtime::DiplomatOption<u8>      // ← tagged struct
{
    Color::default_brightness().into()
        // From<Option<T>> for DiplomatOption<T> via runtime
}

DiplomatOption<T> is literally DiplomatResult<T, ()> in the runtime — the same tagged-union machinery we used for Result, with unit error type. The wire bytes:

Layer 3 — C# raw struct (same pattern as DiplomatResult)

DiplomatOptionU8.cs (codegen)C# raw
namespace DotnetSmoke;

internal static unsafe partial class Raw
{
    [StructLayout(LayoutKind.Sequential)]
    public partial struct DiplomatOptionU8
    {
        [StructLayout(LayoutKind.Explicit)]
        private struct InnerUnion
        {
            [FieldOffset(0)] internal byte value;
            [FieldOffset(0)] internal byte _err;   // ZST in Rust, single byte slack here
        }

        private InnerUnion _inner;

        [MarshalAs(UnmanagedType.U1)]
        public bool IsSome;

        public byte Value => IsSome ? _inner.value : throw new InvalidOperationException("Option is None");
    }
}
Reuse of the Result template. Structurally identical to DiplomatResult_<T>_ColorError — outer Sequential, inner Explicit union, tag at the end via [MarshalAs(U1)]. The codegen can literally emit this through the same result.raw.cs.jinja template with error set to a unit/dummy type. Or have a parallel option.raw.cs.jinja if we want a different field name (IsSome reads more naturally than IsOk for Option).

Layer 4 — C# idiomatic wrapper (tag check, return Nullable)

Color.cs (codegen)C# idiomatic
public static byte? DefaultBrightness()
{
    unsafe
    {
        var result = Raw.Color.DefaultBrightness();
        return result.IsSome ? result.Value : (byte?)null;
        //     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
        //     The whole Option story for value types.
    }
}

Return type is byte? (= Nullable<byte>). Body checks the tag and returns either the value or null. The (byte?)null cast is needed because C#'s ternary requires both branches to have the same type and result.Value is byte, not byte?.

Layer 5 — User call site

idiomatic useuser code

// Pattern 2: ?? default

// Pattern 3: pattern matching (C# 9+)

The decision table

Rust signature C# return type Wire shape How "absence" is signaled Caller pattern
-> Option<Box<T>> T? (nullable ref) plain T* (8 bytes) null pointer c is null / c?.Foo() / c ?? default
-> Option<&T> T? (nullable ref) plain T* (8 bytes) null pointer same as above
-> Option<Primitive> P? (Nullable<P>) DiplomatOption<P> (P bytes + 1 tag + padding) IsSome == false b.HasValue / b ?? default / b is P p
-> Option<Struct> S? (Nullable<S>) DiplomatOption<S> IsSome == false same as primitive
-> Option<Enum> E? (Nullable<E>) DiplomatOption<E> IsSome == false same
-> Option<()> bool? bool (degenerate) false plain bool check (rare)

End-to-end data flow — Path B (the harder one)

1. User calls Color.DefaultBrightness()
Idiomatic wrapper, no params.
↓
2. P/Invoke into Rust
Rust's Color::default_brightness() runs, returns Some(128). The bridge shim's .into() converts to DiplomatOption<u8> with value = 128, is_some = true.
↓
3. 2 bytes returned by value
Native stack carries [0x80, 0x01] — byte 0 = 128, byte 1 = tag (true).
↓
4. C# reads as DiplomatOptionU8
result.IsSome = true via [MarshalAs(U1)].
↓
5. Return Nullable<byte>
return result.IsSome ? result.Value : (byte?)null; → returns (byte?)128.

The None path is identical except step 2 stops at None, step 3's value byte is undefined slack, step 4 sees IsSome == false, step 5 returns null.

What the codegen needs to add

1. New arm in lower_return for Nullable

tool/src/dotnet/gen/method.rs
// Before:
hir::ReturnType::Nullable(_) => unimplemented!("nullable return"),

// After:
hir::ReturnType::Nullable(s) => {
    let return_type = self.lower_success(s);
    // Register a DiplomatOption_<T> struct in a new registry
    // (or reuse the existing result_struct_registry with `()` as error).
    let option_info = self.register_option(&return_type);

        return_type,

4. Return-type rendering — append ? for nullable types

Method signature needs Color? / byte? instead of Color / byte. Cleanest fix: a method DotnetReturnType::idiomatic() that takes a nullable flag and emits "{name}?" when needed. Or just inline the ? conditionally in the signature template.

Pitfalls

1. Value-type nullable boxing. Nullable<T> for primitives doesn't box — it's a value struct. But certain APIs (e.g., generic boxes via object) will box Nullable<T> to null vs the boxed value. Rarely an issue for binding consumers; flagged for completeness.
2. C# 8 nullable-context. Color? only means "might be null" if the project has <Nullable>enable</Nullable> in its csproj. Without it, Color and Color? are the same type at runtime; the annotation is just a hint. The behavior is identical regardless — the binding works either way — but tooling warnings differ.
3. Ternary type inference. IsSome ? result.Value : null fails to compile when result.Value is a primitive — the two branches have incompatible types (byte vs null). The cast (byte?)null is mandatory for primitive paths. For reference types it Just Works.
4. Union slack on None. Same as Result — result.Value on a None result reads union slack bytes (uninitialized). The property guards with throw; never call it without checking IsSome. The codegen always emits the guard, so users can't accidentally read garbage.

TL;DR

  1. Option ≠ Result. Option encodes absence, not failure. Maps to nullable types, not exceptions.
  2. Two code paths. Pointer-shaped T (Box, &T): wire is just a nullable T*, no extra bytes. Value-shaped T (primitive, struct, enum): wire is a DiplomatOption<T> tagged struct (same machinery as Result, unit error).
  3. C# representation matches the wire. Pointer cases return T? (nullable reference). Value cases return T? (Nullable<T>).
  4. Codegen reuses 80% of Result machinery. Same tagged-struct pattern, same nested Sequential + Explicit layout, same exception-free body branching. Just IsSome instead of IsOk and no exception class.
  5. For the user, this is just C# idiom. ?., ??, pattern matching all work naturally. No new abstractions to learn.
