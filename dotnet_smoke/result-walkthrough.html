Result<T, E> — a layered walkthrough

Rust's errors as values meets C#'s exceptions. We're not translating the mechanism — we're translating the intent ("this function can fail"). Idiomatic C# binding throws on Err and returns the Ok value on success.
user code C# idiomatic (auto-gen) C# raw P/Invoke (auto-gen) C ABI contract (binary) Rust shim (macro-gen) throw path

The impedance mismatch

Rust — errors as values rust 
pub fn parse(s: &DiplomatStr) -> Result<Box<Color>, ColorError>
{
    match s {
        b"red"   => Ok(Box::new(Color { brightness: 255 })),
        b"black" => Ok(Box::new(Color { brightness: 0 })),
        _        => Err(ColorError::Unknown),
    }
}

// Caller pattern: type system FORCES handling both
let c = match Color::parse(b"red") {
    Ok(c)  => c,
    Err(e) => { log::warn!("{:?}", e); return; }
};
C# — exceptions C# 
public static Color Parse(string s)
{
    // ... returns Color on success
    // ... throws ColorParseException on failure
}

// Caller pattern: try/catch
try {
    var c = Color.Parse("red");
    // ... use c
} catch (ColorParseException ex) {
    Log.Warn(ex.Error);
    return;
}
What we're trading.
  • Compile-time "must handle" — Rust forces you to pattern-match both arms. C# compiler does not check that you catch ColorParseException.
  • Cost — Rust Result is ~free (one tag check). C# exception throw is ~µs (stack unwinding + allocation). Fine if errors are exceptional; not fine if errors are common in hot paths.
  • Composition — Rust's ? propagates errors cleanly through call chains. C# uses unwinding for the same effect, different mechanism.
We accept these trades because the throw pattern is what every .NET developer expects from every other .NET API. Consistency > preserving Rust's exact semantic.

The example

One method that demonstrates the full Result pipeline: input slice, opaque success type, enum error type. Real-world shape for "construct from input, validation might fail."

dotnet_smoke/src/lib.rs rust source 
pub enum ColorError {
    Unknown   = 0,
    BadFormat = 1,
}

impl Color {
    /// Look up a named color. Recognizes a small fixed set; returns
    /// `ColorError::Unknown` for anything else.
    pub fn parse(s: &DiplomatStr) -> Result<Box<Color>, ColorError> {
        match s {
            b"red"   => Ok(Box::new(Color { brightness: 255 })),
            b"black" => Ok(Box::new(Color { brightness: 0 })),
            b""      => Err(ColorError::BadFormat),
            _        => Err(ColorError::Unknown),
        }
    }
}

Layer 1 — The macro-expanded extern

The bridge macro emits an extern "C" shim that returns a DiplomatResult by value — a repr(C) tagged union sitting on the native stack. No control flow tricks, no panic, no unwinding — the Err case is literally just a different tag value in the same struct.

generated by the macro rust shim 
#[no_mangle]
pub unsafe extern "C" fn Color_parse(
    s: diplomat_runtime::DiplomatStrSlice,
) -> diplomat_runtime::DiplomatResult<*mut Color, ColorError> {
    let s: &[u8] = s.into();
    match Color::parse(s) {
        Ok(boxed)  => DiplomatResult::ok(Box::into_raw(boxed)),
        Err(error) => DiplomatResult::err(error),
    }
}
runtime/src/result.rs (rough shape) runtime 
#[repr(C)]
pub union DiplomatResultPayload<T, E> {
    pub ok: ManuallyDrop<T>,
    pub err: ManuallyDrop<E>,
}

#[repr(C)]
pub struct DiplomatResult<T, E> {
    pub payload: DiplomatResultPayload<T, E>,
    pub is_ok:   bool,    // 1 byte; tag at the end
}

Layer 2 — The C ABI binary layout

For our specific case DiplomatResult<*mut Color, ColorError> on x64 — pointer is 8 bytes, the enum is 4 bytes (default int repr), bool is 1 byte. The union takes max(sizeof(T), sizeof(E)) = 8 bytes; the tag bumps total to 9, padded to 16 bytes for alignment.

Memory layout (Ok case)

byte offset 0..8 8 9..16
field payload.ok is_ok padding
value 0x000001B4_5F2C8010
(Color*)		 0x01
(true)		 —

Memory layout (Err case)

byte offset 0..4 4..8 8 9..16
field payload.err slack of union is_ok padding
value 0x00000000
(ColorError::Unknown)		 unspecified 0x00
(false)		 —
The union overlaps. Bytes 0–8 hold either the Ok payload or the Err payload, never both. The is_ok tag tells the reader which interpretation is valid. Reading the wrong arm is undefined behavior.

Layer 3 — The C# raw struct (the elegant pattern)

The naive approach would be a single [StructLayout(LayoutKind.Explicit)] struct with hand-computed [FieldOffset(N)] for every field — forcing the codegen to maintain a sizeof table and compute the tag's offset per (T, E) pair. Don't do that. The original .NET backend (Benoit, PR #124) used a much cleaner pattern that delegates the math to the CLR.

DiplomatResult_Color_ColorError.cs (codegen) C# raw 
// OUTER struct: Sequential. CLR computes all field offsets for us.
[StructLayout(LayoutKind.Sequential)]
public partial struct DiplomatResult_Color_ColorError
{
    // INNER union: nested private type with Explicit layout.
    // Only the OVERLAP needs Explicit — and both arms always sit at offset 0.
    [StructLayout(LayoutKind.Explicit)]
    private unsafe struct InnerUnion
    {
        [FieldOffset(0)] internal Raw.Color* ok;
        [FieldOffset(0)] internal ColorError err;
    }

    private InnerUnion _inner;          // CLR places at offset 0

    [MarshalAs(UnmanagedType.U1)]        // force bool to 1 byte (matches Rust)
    public bool isOk;                     // CLR places after _inner

    public Raw.Color* Ok  => _inner.ok;
    public ColorError Err => _inner.err;
}
Zero offset computation in the codegen. The only [FieldOffset(N)] values are 0 — a constant. Every other offset (_inner's position, isOk's position, struct total size, alignment) is computed by the CLR from the field type declarations alone. The codegen is a name-shuffler; the CLR is the layout computer.
How the CLR figures out sizes. Type declarations are all the CLR needs:
  • internal Raw.Color* ok; → CLR knows pointer = 8 bytes on x64
  • internal ColorError err; → CLR knows int-repr enum = 4 bytes
  • → InnerUnion size = max(8, 4) = 8 bytes
  • private InnerUnion _inner; → CLR places at offset 0
  • [MarshalAs(U1)] bool isOk; → CLR places at offset 8
  • → struct size = round_up(9, 8) = 16 bytes
Same 16 bytes Rust's repr(C) computes. Two compilers, same C ABI rules, identical layouts — without any direct communication.
[MarshalAs(UnmanagedType.U1)] on the bool. Without it, C# defaults to marshaling bool as a 4-byte BOOL (a Win32 convention). U1 forces 1 byte, matching Rust's bool width. With this marker we can use bool isOk directly instead of byte IsOk with manual != 0 checks.
The principle: delegate layout to the target compiler. Where possible, generate type declarations that cause values to be computed — don't pre-compute the values yourself.
  • Need overlap? [FieldOffset(0)] ×2 — the only literal allowed (it's always zero).
  • Need to know union size? Wrap in a nested Sequential — CLR sums fields.
  • Need total struct size? Don't — emit fields, CLR sums them.
  • Need alignment? Don't — CLR picks max of field alignments.
Rust does the same thing on its side via repr(C). Both compilers walk the same C-ABI rules from the same type declarations and arrive at identical byte layouts.

ABI parity — Rust and C# produce the same 16 bytes

The codegen never tells either compiler what bytes to produce. Both compilers independently apply the C ABI rules to their respective type declarations and arrive at byte-identical output. Here's the parity laid out — same field name on the left and right, same offset in the middle.

Ok case — the wire carries a pointer

Rust field offset bytes C# field
value.ok: *mut Color 0..8 10 80 2C 5F
B4 01 00 00		 _inner.ok: Color*
is_ok: bool 8 01 isOk: bool [U1]
struct padding (repr(C)) 9..16 -- -- --
-- -- -- --		 struct padding (Sequential)

Err case — the wire carries an enum value (lower 4 bytes), upper 4 are slack

Rust field offset bytes C# field
value.err: ColorError 0..4 00 00 00 00 _inner.err: ColorError
union slack (uninitialized) 4..8 ?? ?? ?? ?? union slack — same uninit bytes
is_ok: bool 8 00 isOk: bool [U1]
struct padding (repr(C)) 9..16 -- -- --
-- -- -- --		 struct padding (Sequential)
Same 16 bytes, two independent compilers.
  • Rust's rustc sees #[repr(C)] struct DiplomatResult<T, E> { value: union, is_ok: bool } and walks the C-ABI layout rules.
  • The CLR sees [StructLayout(Sequential)] struct DiplomatResult_Color_ColorError { InnerUnion _inner; bool isOk; } and walks the same rules.
  • Neither compiler knows the other exists.
  • The bytes match because the rules are public and deterministic.
What makes this parity hold mechanically
  1. Field names don't have to match — Rust calls the union value, C# calls it _inner. The CLR / rustc don't care; they only look at types and order.
  2. Field order matters absolutely — Rust declares value before is_ok. C# must declare _inner before isOk. Swap the order, the tag's offset changes.
  3. Field types must be ABI-equivalent — Rust's *mut Color is 8 bytes; C# must use a pointer-typed field (Color* or IntPtr), not an int. bool must be size 1 (the [MarshalAs(U1)] directive).
  4. Layout kinds enforce C ABI on both sides — Rust's #[repr(C)] says "use C rules"; C#'s [StructLayout(Sequential)] says "use C rules." They're saying the same thing in different syntaxes.

The codegen's actual job in this parity

Look at what the codegen has to write into the C# struct definition:

What the codegen writes Why it matters for ABI
[StructLayout(LayoutKind.Sequential)] Tells CLR "use C ABI rules" — matches Rust's #[repr(C)]
[StructLayout(LayoutKind.Explicit)] (inner) Tells CLR "I'll specify offsets" — only needed for the union part
[FieldOffset(0)] on both arms Tells CLR "these two fields alias at byte 0" — the union semantic. Always 0, never computed.
Color* ok; + ColorError err; Field types — CLR derives field sizes from these. Must be ABI-equivalent to Rust's types.
InnerUnion _inner; first, bool isOk; second Field order — must match Rust's declaration order. Swap them and the layout shifts.
[MarshalAs(UnmanagedType.U1)] Forces bool to be 1 byte — matches Rust's bool on the wire (otherwise C# defaults to 4-byte BOOL)

Six annotations, two type names. No sizeof table, no offset arithmetic, no Size = N hint. The codegen's job is to write declarations that cause the right bytes to materialize on the C# side — declarations that mirror what Rust already declared on its side. Both compilers do the layout math from those declarations, independently, and arrive at the same 16 bytes.

Layer 4 — The exception class

Per-error exception type, generated alongside the result struct. The error enum value rides inside as a public property; the message comes from its string form. Catchable by name in C# patterns.

ColorParseException.cs (codegen) C# exception 
namespace DotnetSmoke;

public class ColorParseException : Exception
{
    public ColorError Error { get; }

    public ColorParseException(ColorError error)
        : base($"Color.Parse failed: {error}")
    {
        Error = error;
    }
}
One exception class per error type, not per fallible method. All Color methods that fail with ColorError share ColorParseException (we may rename to ColorException for that reason). If we later add a method that fails with a different error enum, that's a separate exception class. Caller writes catch (ColorException ex) regardless of which method threw.

Layer 5 — The idiomatic wrapper (the throw point)

The user-facing C# method. Takes a managed string, hands an opaque Color back, throws ColorParseException on failure. This is the function the IronRDP devs (or anyone else) actually calls.

The Rust source — what the dev wrote rust 
impl Color {
    pub fn parse(s: &DiplomatStr)
        -> Result<Box<Color>, ColorError>
    {
        match s {
            b""      => Err(ColorError::BadFormat),
            b"red"   => Ok(Box::new(Color { brightness: 255 })),
            b"black" => Ok(Box::new(Color { brightness: 0 })),
            _        => Err(ColorError::Unknown),
        }
    }
}
The generated C# — Color.cs C# idiomatic 
public static Color Parse(string s)
{
    unsafe
    {
        byte[] sBytes = Encoding.UTF8.GetBytes(s);
        fixed (byte* sPtr = sBytes)
        {
            var result = Raw.Color.Parse(new DiplomatSliceU8
            {
                Ptr = sPtr,
                Len = (nuint)sBytes.Length,
            });

            if (!result.isOk)
            {
                throw new ColorParseException(result.Err);
            }
            return new Color(result.Ok);
        }
    }
}

Line-by-line — what each piece does

C# line What it does + which earlier layer it relates to
public static Color Parse(string s) Idiomatic return type is Color (the wrapper class) — error is signaled by exception, not in the type. Param is string — caller passes managed UTF-16.
byte[] sBytes = Encoding.UTF8.GetBytes(s); Encode UTF-16 string → UTF-8 bytes. Required because Rust's &DiplomatStr wants UTF-8. From the &DiplomatStr walkthrough.
fixed (byte* sPtr = sBytes) Pin the byte array so the GC can't move it during the FFI call. Required for any slice passed by pointer.
var result = Raw.Color.Parse(...) The actual P/Invoke. Returns a DiplomatResult_Color_ColorError struct by value — the 16 bytes we just walked through. This is where the ABI parity from the previous section is used.
if (!result.isOk) Reads byte 8 of the struct — the tag. C# sees bool because of [MarshalAs(U1)]; reads as a normal bool. The non-negotiable check from the union mechanics.
throw new ColorParseException(result.Err) Reads bytes 0..4 of the union as ColorError (the active arm when !isOk). Wraps in the per-error-type exception class.
return new Color(result.Ok) Reads bytes 0..8 of the union as Color* (the active arm when isOk). Wraps in the IDisposable wrapper class — same pattern as every opaque return.
What the codegen actually has to assemble for this method:
  • Encode + pin scaffolding — comes from the &DiplomatStr input lowering (already shipped)
  • Result struct binding — var result = Raw.Color.Parse(...). The struct type name (DiplomatResult_Color_ColorError) is the same one in the result registry — emitted once, used here.
  • Tag check + throw — driven by method.is_fallible() in the template. The exception class name is derived from method.error_type on MethodInfo.
  • Ok unwrap — kind-specific. new Color(result.Ok) for opaque returns; return result.Ok; for primitives; return Point2D.FromFFI(result.Ok); for structs.
Each piece exists somewhere we've already designed. The template just composes them in order.

What this looks like in the template

End-to-end data flow

Ok path

1. User calls Color.Parse("red")
Idiomatic wrapper receives the string.
↓
2. UTF-8 encode + pin
sBytes = [0x72, 0x65, 0x64], pinned via fixed.
↓
3. Raw extern call
Raw.Color.Parse(DiplomatSliceU8{ Ptr, Len=3 }) → Rust runs the match, hits the b"red" arm, allocates a Color, builds DiplomatResult::ok(boxed.into_raw()).
↓
4. Result returned by value (16 bytes)
Bytes 0..8 = pointer to Color, byte 8 = 0x01 (isOk = true).
↓
5. C# checks isOk
result.isOk == true → enter the Ok branch.
↓
6. Wrap and return
return new Color(result.Ok); — IDisposable wrapper around the raw pointer. Caller receives a normal Color value.

Err path

1. User calls Color.Parse("rainbow")
Idiomatic wrapper receives the string.
↓
2. UTF-8 encode + pin
Same as Ok path — no special handling on the input side.
↓
3. Raw extern call
Rust's match falls through to the _ arm, returns DiplomatResult::err(ColorError::Unknown). Same 16-byte struct, different tag.
↓
4. Result returned by value (16 bytes)
Bytes 0..4 = ColorError::Unknown (= 0), byte 8 = 0x00 (isOk = false).
↓
5. C# checks isOk
!result.isOk → enter the Err branch.
↓
6. Throw
throw new ColorParseException(result.Err); — stack unwinds back to the caller's try/catch.
↓
7. fixed block exits, exception propagates
The fixed scope ends cleanly during unwinding (sBytes becomes unpinned, but we don't care — no more native code is running). Caller's catch (ColorParseException ex) receives the exception.

Side by side — match vs try/catch

Rust: match handles both arms rust 
match Color::parse(b"rainbow") {
    Ok(c) => {
        // use c (compiler tracks: type is Box<Color>)
    }
    Err(ColorError::Unknown) => {
        log::warn!("unknown color");
    }
    Err(ColorError::BadFormat) => {
        log::warn!("malformed input");
    }
}
C#: try/catch handles the throw C# 
try {
    using var c = Color.Parse("rainbow");
    // use c (compiler tracks: type is Color)
}
catch (ColorParseException ex) when (ex.Error == ColorError.Unknown) {
    Log.Warn("unknown color");
}
catch (ColorParseException ex) when (ex.Error == ColorError.BadFormat) {
    Log.Warn("malformed input");
}
The when filter is C#'s match-arm equivalent. Pattern-matching on the error enum is what match Err(...) does in Rust. C# 6+ supports exception filters (catch (T) when (predicate)) which gives you the same per-variant dispatch without a giant switch inside the catch block.

Pitfalls

1. Enum repr must match between Rust and C#. Diplomat enums default to int-repr (4 bytes) on both sides — that's fine, the CLR sees the C# enum as 4 bytes and lays out the union accordingly. If a Rust enum ever uses #[repr(u8)] or similar, the C# generated enum has to match (e.g. : byte underlying type). The codegen handles this by reading the repr attribute from HIR and emitting the matching C# underlying type.
2. Union slack bytes are unspecified. When Rust returns Err, the Ok bytes hold whatever was on the stack — not zero, not the err payload zero-extended. C# code must check isOk before reading Ok or Err. Reading the wrong arm is UB — pointer-shaped garbage in the Err case, enum-shaped garbage in the Ok case. (Mitigated by the property getters: callers only see .Ok and .Err, which the codegen wraps in if (result.isOk) ... checks at every call site.)
3. fixed block lifetime + exception unwinding. When we throw inside a fixed block, the unwinding unpins cleanly — that's how try/catch always works. No special care needed. Just don't structure the code such that the raw pointer escapes the fixed scope.
4. Exception cost in hot paths. throw new ColorParseException(...) costs ~µs (allocation + stack capture). If a Rust API returns Result<T, E> as the normal way to signal "not found" or "try again" — and the caller hits the Err path often — exceptions become a real perf liability. In that case the Rust API is mis-designed (should be Option<T> or a stream pattern); don't try to fix it in the binding.
5. Result<Result<..>> nesting. Diplomat doesn't let you return nested Results across FFI — the HIR rejects them. If Rust has nested fallibility, flatten it on the Rust side before exposing.

Summary — three-line story

  1. Rust says "errors are values; returns a tagged union." Result<T, E> rides the stack as a repr(C) struct.
  2. C# binding says "errors throw; success returns." Idiomatic wrapper checks the tag, returns the Ok or constructs+throws the exception.
  3. User says try { var x = Foo.Parse(s); } catch (FooException ex) { ... }. Same shape they use for every other .NET API.

Errors-as-values is the mechanism. "This can fail and the caller has to handle it" is the intent. We translate the intent into the target language's idiom — not the mechanism literally. That's the whole job of a binding generator.
