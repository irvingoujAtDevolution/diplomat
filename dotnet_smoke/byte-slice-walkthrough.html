&[u8] and &mut [u8] — a layered walkthrough

Primitive byte slices crossing FFI. This is the IronRDP unblock. uniffi only supports the immutable side; &mut [u8] is exactly what RDP frame decoding needs — a caller-owned buffer that Rust writes into and the caller reads back. Diplomat handles both natively.
user code C# idiomatic (auto-gen) C# raw P/Invoke (auto-gen) C ABI contract (binary) Rust shim (macro-gen) mutation point

The two examples

Two methods on Color illustrate the immutable vs mutable case. Each is the minimal shape that exercises its lowering path end-to-end:

  • Immutable: checksum(bytes: &[u8]) -> u32 — bytes come in, primitive goes out, Rust reads only.
  • Mutable: fill_buffer(&self, buf: &mut [u8]) — caller's buffer goes in empty, comes back filled with self.brightness.

Layer 1 — Rust source (what the dev writes)

dotnet_smoke/src/lib.rs rust source 
impl Color {
    /// Immutable byte slice — Rust reads, never writes.
    pub fn checksum(bytes: &[u8]) -> u32 {
        bytes.iter().map(|&b| b as u32).sum()
    }

    /// Mutable byte slice — Rust writes through, caller sees the writes.
    /// This is the shape IronRDP needs for frame decoding.
    pub fn fill_buffer(&self, buf: &mut [u8]) {
        for b in buf.iter_mut() {
            *b = self.brightness;
        }
    }
}
The key distinction. &[u8] is a read-only borrow (no Rust-side mutation). &mut [u8] is an exclusive mutable borrow — Rust can write through, and the caller observes the writes after the call returns. The borrow checker enforces exclusivity on the Rust side; the C# binding has to honor it by hand.

Layer 2 — Macro-expanded extern (what diplomat::bridge emits)

Both &[u8] and &mut [u8] get rewritten to DiplomatSlice / DiplomatSliceMut respectively — a repr(C) fat pointer struct. Same shape; the only difference is the pointer's mutability marker.

checksum — generated extern rust shim 
#[no_mangle]
pub unsafe extern "C" fn Color_checksum(
    bytes: DiplomatSlice<u8>,
) -> u32 {
    let bytes: &[u8] = bytes.into();
    Color::checksum(bytes)
}
fill_buffer — generated extern rust shim 
#[no_mangle]
pub unsafe extern "C" fn Color_fill_buffer(
    handle: *const Color,
    buf: DiplomatSliceMut<u8>,
) {
    let this: &Color = &*handle;
    let buf: &mut [u8] = buf.into();
    this.fill_buffer(buf);
}
runtime/src/slices.rs — the two structs runtime 
#[repr(C)]
pub struct DiplomatSlice<'a, T> {
    ptr: *const T,    // immutable pointer
    len: usize,
    phantom: PhantomData<&'a [T]>,
}

#[repr(C)]
pub struct DiplomatSliceMut<'a, T> {
    ptr: *mut T,      // mutable pointer — same 16 bytes on the wire
    len: usize,
    phantom: PhantomData<&'a mut [T]>,
}
ABI: identical 16 bytes. *const T and *mut T have the same machine representation — a pointer is a pointer. The mutability marker only affects what Rust / the C# binding are allowed to do, not how the bytes line up. This is why the two structs need distinct C# types (so the binding tracks the intent) even though their layout is identical.

Layer 5 — C# idiomatic wrapper

Here's where the two diverge. Immutable takes ReadOnlySpan<byte>; mutable takes Span<byte>. Both pin via fixed directly — no encoding step (caller already has bytes), no allocation (no intermediate byte[]). Zero-copy.

Color.cs — Checksum (immutable) C# idiomatic 
public static uint Checksum(ReadOnlySpan<byte> bytes)
{
    unsafe
    {
        fixed (byte* bytesPtr = bytes)
        {
            return Raw.Color.Checksum(new DiplomatSliceU8
            {
                Ptr = bytesPtr,
                Len = (nuint)bytes.Length,
            });
        }
    }
}
Color.cs — FillBuffer (mutable) C# idiomatic + mut 
public void FillBuffer(Span<byte> buf)
{
    unsafe
    {
        if (_inner == null) throw new ObjectDisposedException(nameof(Color));
        fixed (byte* bufPtr = buf)
        {
            Raw.Color.FillBuffer(_inner, new DiplomatSliceMutU8
            {
                Ptr = bufPtr,
                Len = (nuint)buf.Length,
            });
        }
        // After this point, `buf` reflects Rust's writes.
    }
}
Why Span<T> instead of byte[]?
Span<byte> accepts byte[], stackalloc byte[N], slices of larger arrays (arr.AsSpan(start, length)), and unmanaged memory. byte[] only accepts a managed array. For an FFI surface that's supposed to be flexible, Span is the right choice. fixed (byte* p = span) has worked on Span<T> since .NET 7.

End-to-end data flow for fill_buffer

This is the IronRDP path — caller-owned buffer, Rust mutates in place. The reverse direction (writes propagating back to C#) is the meaty step.

1. User allocates
Span<byte> buf = stackalloc byte[4]; — 4 bytes on the stack, initialized to zero. buf points at it.
↓
2. Idiomatic wrapper enters
Disposed check runs (instance method on Color). No allocation, no copy.
↓
3. fixed block pins the buffer
fixed (byte* bufPtr = buf) tells the GC: don't move buf's backing storage until this block exits. Even though stackalloc memory isn't subject to GC, the codegen emits fixed uniformly so the Span source doesn't matter.
↓
4. Build the fat pointer struct
new DiplomatSliceMutU8 { Ptr = bufPtr, Len = 4 } — 16 bytes by value on the native stack.
↓
5. P/Invoke crosses the boundary
Blittable struct, raw memcpy onto native stack. Rust's Color_fill_buffer receives handle and buf.
↓
6. Rust rehydrates &mut [u8]
buf.into() calls From<DiplomatSliceMut<u8>> for &mut [u8]: slice::from_raw_parts_mut(ptr, len). buf is now an exclusive mutable reference into the C# caller's memory.
↓
7. Rust writes through
for b in buf.iter_mut() { *b = self.brightness; } — each *b = 128 issues a store to the address pointed to by bufPtr, which is the caller's stack-allocated buffer.
↓
8. Rust returns (no return value)
Color_fill_buffer exits. Native stack unwound.
↓
9. fixed block ends, C# resumes
bufPtr is now invalid. But buf (the Span) is unchanged — it still points at the same 4 bytes, which now hold [128, 128, 128, 128]. Caller observes the writes.

Same address, same length. Bytes changed from 00 to 0x80 (= 128) because Rust's *b = self.brightness wrote through the pointer. Zero copies, zero allocations — the buffer never left the caller's stack.

Why this matters — the IronRDP unblock

uniffi can't do &mut [u8]. PR #2878 added immutable &[u8] support to uniffi, but mutable byte slices are still unsupported — every "fill this buffer" API has to either (a) return a fresh Vec<u8> (allocation + copy + free on every call) or (b) thread the buffer through some custom binding code. For IronRDP's frame decoding — which happens 60 times per second with multi-megabyte buffers — option (a) is a non-starter and option (b) defeats the purpose of having an FFI generator.
Diplomat handles &mut [u8] natively. The lowering machinery is identical to &[u8] modulo: (1) the idiomatic param is Span<byte> not ReadOnlySpan<byte>, (2) the raw struct is DiplomatSliceMutU8 not DiplomatSliceU8. The fixed block, the call site, the byte-level data flow — all identical. The abstraction we built for slices generalizes cleanly.

        }

Pitfalls

1. Empty Span<byte> & null pointer. fixed (byte* p = emptySpan) may set p to null. Rust's From<DiplomatSliceMut> already handles this (null + len 0 → empty slice). Don't add C#-side null guards — they'd be redundant and break the empty case.
2. Span lifetime escapes are the user's problem, not ours. If the caller stashes the Span<byte> after the call returns, that's fine — the Span still points at valid memory (the caller's storage). The pointer we extracted via fixed is invalid post-block; the Span isn't. No special care needed.
3. stackalloc + large buffers. stackalloc byte[N] for large N blows the stack. .NET 7+ has stackalloc guarded by a size limit, but if callers pass IronRDP-sized frames (megabytes), they should use ArrayPool<byte>.Shared.Rent(n) or a regular byte[]. Our binding accepts any of them via Span<byte>; that's the caller's choice.
4. Concurrent access during the call. The caller must not touch buf on another thread while Rust is writing through. The &mut borrow in Rust enforces single-writer; the C# binding can't enforce it across threads. Document the API as "not thread-safe during the call" — same rule that applies to any FFI mutable-buffer API.

Summary — the one-line story per slice flavor

  1. &DiplomatStr: caller's string → allocate UTF-8 byte[] → pin → cross. One copy (the encode), one allocation.
  2. &[u8]: caller's ReadOnlySpan<byte> → pin → cross. Zero copies, zero allocations.
  3. &mut [u8]: caller's Span<byte> → pin → Rust writes through → caller observes. Zero copies, zero allocations, writes propagate. The IronRDP unblock.
